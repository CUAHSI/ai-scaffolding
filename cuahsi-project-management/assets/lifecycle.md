# Lifecycle cases

Load the branch matching the request. The main skill owns the common schema, confidentiality, participation, and sign-off rules; these cases specialize timing and authority.

## Existing project without a charter

Use the main workflow's checkpoint rule rather than backdating a kickoff to the award or requiring a second award-stage meeting. Ask which checkpoint applies if unclear. Use current authorized plans and discussion, keeping historical proposal wording distinct from the current interpretation.

## Core Award Activity

Confirm which co-PI owns this activity separately from the overall award's PI role. A change of owning co-PI requires explicit confirmation, not inference from who attends or reviews. Decision-PR tags can include both roles without changing activity ownership. Apply the common workflow using that confirmed ownership.

## Existing charter or requested revision

1. Identify the baseline charter, its version, canonical code, approval record, and proposed changes. Preserve that baseline and its approval as historical evidence. A routine update, decision, or generic request to tidy the charter is not permission to change its commitments.
2. Establish that a **Wayfinder or grilling session** authorizes the revision. Accept a supplied, attributable session record naming the participants and agreed changes; if its scope or authority is unclear, ask. If no session has happened, stop before altering the charter: show the proposed questions and ask the user to run Wayfinder/grilling, or explicitly agree to conduct a grilling session in this conversation. Merely labeling a routine edit a re-grill is not a session.
3. If running the session here, identify the human participants and approval role, challenge the reasons, scope, dependencies, and trade-offs of the proposed change, and obtain an explicit account of the agreed changes and unresolved points. Only then draft the candidate. A supplied session record may support drafting, but does not by itself establish approval of the resulting charter version.
4. Change only what the session authorizes, preserving unaffected commitments and source wording. A changed canonical accounting code requires explicit confirmation, not derivation from a slug or repository. Record the baseline/version and session reference in the candidate source documents and summarize the material changes for review.
5. Apply the common participation and sign-off workflow to the candidate, including its status determination. Preserve the baseline approval record separately.
6. Deliver the candidate separately. If a changed proposal is still unresolved, deliver questions or a handoff, not a silently amended or supposedly approved charter.

When a request contains both a charter and a new kickoff, this branch still applies: the presence of an approved baseline cannot be bypassed by choosing a different mode label. Automatic conflict detection against accumulated decision logs is later work; this slice handles the revision that the user presents.
