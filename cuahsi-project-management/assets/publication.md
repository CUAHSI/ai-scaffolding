# Publish project information (CAM-1634)

Use this procedure for an explicit `cuahsi-project-management publish` request, a request to store an in-progress charter or rename its path, or the user's post-kickoff **"this is approved"** follow-up defined in [Publish kickoff documents](../SKILL.md#5-publish-kickoff-documents). That follow-up authorizes committing/pushing the approved documents on a topic branch and opening a PR targeting `develop`, without another publication request; it authorizes no direct push to `develop`, merge, or promotion to `main`. Publication remains separate from merely drafting kickoff output. Charter revision and review history live in Git commits and GitHub PRs, not charter metadata. Keep existing AI/review fields for policy and decision artifacts, recording human review only from verified evidence; these fields do not certify charter approval. Team review and approval take place wholly outside the skill through GitHub PRs. Use GitHub CLI and Git already available in the environment; no separate application, hosting, transcript ingestion, or email service is introduced.

## ProjectStream submission rule

Every change to `CUAHSI/CUAHSI-ProjectStream` made through this skill, whether from `kickoff`, `revise`, a rename, navigation, or policy work, reaches the repository only through a pull request. Never push directly to `develop`, `main`, or any other ProjectStream branch, including for a small follow-up fix to a file already on `develop`. Start a topic branch from the latest remote `develop`, push only that branch, and open a PR whose base is `develop`.

Name the branch for the action executed, in the form `<action>-<ShortName>-<summary>`: the action word first (`kickoff`, `revise`, `rename`, or the action actually performed), then the case-preserved project shortname, then a short hyphenated summary of what the change does. Replace spaces and characters Git disallows with hyphens, and keep the summary specific. Examples: `kickoff-FIMBox-project-initiation` and `revise-FIMBox-simplify-charter-header`. Give the PR a title that reads the same way, such as `kickoff - FIMBox project initiation` or `revise - FIMBox - simplify charter header`.

Two cases cannot follow the develop-PR form. A bootstrap commit for an empty repository has no base branch to target, so it follows step 3 with its separate approval. A promotion to `main` remains a focused PR from a fresh topic branch (step 5) and is still never a direct push. Both are PR-only or explicitly approved; neither permits a direct push to `develop`.

## 1. Establish destination and authority

Use `CUAHSI/CUAHSI-ProjectStream`, the [skill's fixed publication destination](../SKILL.md), without asking the user to choose a central repository. Confirm the responsible practice owner, access administrator, canonical accounting code, shortname, exact charter source revision, intended proposal storage on `develop` or promotion PR targeting `main` (or path-only rename), and all related project/activity repositories. Collect or explicitly confirm the shortname with the user, preserving its case: it is a human-readable folder suffix, not a new identity. A slug/title may support a proposal, but is not confirmation; keep a missing shortname pending rather than blindly deriving it from the slug. Read the existing central policy or start a candidate from the [repository policy template](repository-policy-template.md). Tony approves tooling changes; credential/hosting work has a named, explicitly delegated owner. Ask for missing administrative authority instead of choosing a staff team or changing permissions unilaterally.

Inspect ProjectStream's visibility, contents, branches, and current project files with authenticated read-only operations. Verify that the authorized local checkout targets this repository; a different current repository or Git remote is not the central destination. If ProjectStream is unavailable or not private, report the blocker rather than create or use a replacement. An empty repository has no charter and may have no branches even when its configured default branch is `main`. A failed request is not evidence of absence. Keep live project documents and audit data outside this source checkout and the installed skill. Use an explicitly authorized private workspace; retain existing files and user changes.

**Done when:** the destination and requested writes are explicit, and missing identity, policy, credentials, or write authorization is listed. Without a canonical code or confirmed shortname, offer a plan and clarification questions but create or rename no project directory on either branch.

## 2. Audit effective access

Complete the policy's access configuration and verification record before committing project content, including drafts. Compare all effective access paths against an authorized employee roster, not organization membership. Check private visibility, organization base permission, organization owners, all direct collaborators, teams and inherited/nested membership, pending invitations, apps, deploy keys, and automation. Employees need write permission to propose and merge decisions; external collaborators receive exports through the separate export workflow. Authorized machine access must have a named accountable owner.

For the confirmed repository, representative read operations are:

```sh
gh repo view CUAHSI/CUAHSI-ProjectStream --json isPrivate,defaultBranchRef,viewerPermission
gh api repos/CUAHSI/CUAHSI-ProjectStream/collaborators --paginate
gh api 'repos/CUAHSI/CUAHSI-ProjectStream/collaborators?affiliation=outside' --paginate
gh api repos/CUAHSI/CUAHSI-ProjectStream/teams --paginate
gh api repos/CUAHSI/CUAHSI-ProjectStream/invitations --paginate
gh api repos/CUAHSI/CUAHSI-ProjectStream/keys --paginate
gh api repos/CUAHSI/CUAHSI-ProjectStream/rulesets --paginate
gh api repos/CUAHSI/CUAHSI-ProjectStream/rules/branches/main
gh api repos/CUAHSI/CUAHSI-ProjectStream/rules/branches/develop
```

Also inspect organization permissions/owners, each team's members and children, applicable branch protections including inherited rules, and installed GitHub Apps using appropriately authorized administration APIs. Resolve actual account/team names from read results before generating commands. Keep roster and audit details private; record references rather than HR contents or credentials. An inaccessible API is `unverified`, not an empty access list.

Test staff read and nonstaff denial using explicitly authorized test identities with adequate credentials/SSO authorization. For a new repository, first audit access configuration, then perform the explicitly approved non-sensitive bootstrap in step 3 so read/merge probes have a real target. Complete those probes before committing any charter content; repeat read checks against the approved charter after publication. Record bootstrap probes as such, not as an approved-charter read. A 404 from a narrowly scoped token or an unauthenticated request alone cannot distinguish an access restriction from inadequate credentials. Record identities, adequate scope, timestamp, observation, and result without tokens. Confirm employee decision-PR review, merge, and self-merge through a harmless synthetic PR. Review counts, author-approval restrictions, CODEOWNERS requirements, push restrictions, or inherited rules must not effectively prohibit the agreed employee self-merge policy. Do not weaken organization rules or remove collaborators without the owner's explicit approval; hand off the exact conflict to the access administrator.

**Done when:** each access check is `verified`, `failed`, or `unverified` with evidence. Publish project content only when the complete audit and staff/nonstaff/merge checks are verified. If blocked, provide templates and a delegated checklist; only the separately authorized non-sensitive bootstrap may proceed before branch-dependent probes pass. Do not claim staff-only access or operational acceptance. Synthetic checks establish scenario behavior, not live permissions.

## 3. Establish repository layout and branches

Under the confirmed policy, `main` contains approved charter snapshots and their decision logs through the external GitHub PR process; `develop` contains proposals. The branch identifies proposal status without document-level or item-level proposal labels. Both use:

```text
POLICY.md
.github/pull_request_template.md
projects/<accounting-code>-<shortname>/charter.md
projects/<accounting-code>-<shortname>/decision-log.md
```

The adjacent decision log is required for a charter snapshot on `main`. A proposal does not invent approval metadata or decision entries. For example, code `A250366S013` and confirmed shortname `FIMBox` give `projects/A250366S013-FIMBox/`. Use the following directory contract for creation, reuse, and renames:

- **Identity:** read the original accounting code from charter identity and the policy's directory mapping. Never infer identity by splitting on hyphens: both codes and shortnames may contain them. The shortname and slug are not canonical keys. Unknown or conflicting identity/path metadata remains a blocker until confirmed.
- **Safe segment:** validate the confirmed shortname, code component, and complete `<accounting-code>-<shortname>` as safe single path segments before writes. Require nonempty values; reject `.`/`..`, traversal, absolute paths, `/` or `\`, control/NUL characters, filesystem-reserved names/characters, trailing spaces/dots, and names exceeding destination filesystem limits. Verify the resolved directory stays directly under `projects/`, without symlink redirection. Propose a safe alternative shortname for confirmation rather than silently stripping characters, lowercasing, or slugifying it.
- **Encoding:** if the original code cannot be used safely, agree a reversible accounting-code encoding and record the original code, encoded component, encoding/decoding rule, confirmed shortname, and exact directory in the policy before use. Preserve the original code in charter identity. Record `none` when no encoding is needed. This filename encoding is distinct from URL escaping: build URLs by URL-escaping the actual recorded segment, including any literal encoding markers.
- **Uniqueness:** inspect policy mappings, charter identity fields, existing directories (including legacy names), and pending publication PRs on `main` and `develop`. Use one project directory per accounting code per branch, including multi-repository projects, with the same agreed mapping across branches. Reuse an existing mapping for that code; a different requested suffix requires an explicit path-only rename, not a second directory. Block an occupied destination, a case-folding/filesystem-equivalent collision, an ambiguous encoding, or duplicate directories for the same accounting code even under different shortnames. Stop for reconciliation rather than overwrite, merge, or invent an identity. A project's own corresponding `main`/`develop` copies are not duplicate projects. The verified source of the same requested move is not a second destination occupant; case-only moves still need the safe workspace handling below.

Record the confirmed mapping in the [repository policy](repository-policy-template.md); it is current directory metadata. An absent or historical Shortname field in an existing charter is not silently backfilled or rewritten to match it. Build canonical navigation URLs using `blob/main`, never the changing default branch or `develop`.

For an empty repository, obtain approval for a bootstrap commit containing only non-sensitive policy/navigation and the [decision PR template](decision-pr-template.md) at `.github/pull_request_template.md`. Create `main` and then `develop` from that bootstrap, make `main` the default, and read back both refs/configuration. The bootstrap has no approved charter. For existing repositories, propose focused configuration PRs; preserve contents and policy. Adding branches, publishing charter content, granting access, and merging PRs are distinct authorized actions. Confirm the intended changes rather than treating a read/plan request as permission to write. Never force-push, replace history, or merge a whole draft branch into the approved branch.

**Done when:** branches/layout are read back as configured, or their exact remaining setup/delegation is reported. Record Tony's actual tooling approval and the responsible administrator; drafting policy is not approval of it.

### Path-only rename

Use this branch only when the user explicitly requests a path-only rename. Apply steps 1–3, including the unchanged access audit, and the same write/merge authorization and repository-rule requirements in step 5; replace charter selection/promotion in steps 4–5 with these rename checks, then continue to navigation in step 6.

1. Establish the existing project's accounting code from charter/policy metadata, source paths and revisions on each affected branch, and confirmed destination shortname. Apply the directory contract above, including legacy directories and pending PRs. If only publication was requested and an existing path differs, ask before moving it. Report duplicate or conflicting mappings as blockers, not permission to consolidate projects.
2. Move the existing project directory on each explicitly authorized branch through focused changes. Preserve charter/log bytes exactly, including all historical metadata, commitments, log entries/order/IDs, and historical baseline references. Move other existing project files unchanged; initialize no new charter, log, or decision. Keep Git history and immutable commit links retrievable through normal rename commits; never rewrite history or force-push. Preserve each branch's own snapshot/proposal contents rather than copying one branch over the other. For a case-only rename, verify a vacant temporary segment if the workspace filesystem needs a two-step move, then verify the final spelling.
3. Update the policy mapping (original code, encoding, shortname, old/new paths and rename commit evidence), central README/index navigation, and every affected related-repository link under its normal authorization/PR process. Historical immutable references inside the charter/log remain untouched. If a branch or link change lacks authorization, list that migration gap individually; do not create a replacement project or claim completion.
4. Show the rename/navigation-only diff before writes. Compare source and destination charter/log bytes before and after merge, verify the old directory is absent and only one directory maps to the code on each migrated branch, and read back active navigation URLs. Recheck destination occupancy and latest branch state on retry/concurrent edits; an already completed identical rename needs no duplicate PR. Report partial moves and link gaps explicitly.

A path-only rename is not a new project or charter-content revision: it needs no new kickoff or Wayfinder/grilling session. Existing history remains attached to unchanged bytes; it does not authorize content changes. If the user also asks to revise commitments or charter metadata, separate that candidate from the move and hand off its review and approval through an external GitHub PR.

## 4. Select and screen the exact charter

Read the complete [charter template](charter-template.md) and identify the exact source revision and requested diff. For new or revised charter content, the header contains only `Date last modified`; the first section is a plain-language `Project summary`. Omit AI-drafted, Reviewed by, Version, and Status header fields, item-level proposed labels, and the Sign-off section. Git commits and PRs carry revision and review history. A pure path-only rename preserves existing bytes, including unrelated historical metadata, rather than applying a content migration.

For in-progress storage, retain unresolved planning values honestly and target only `develop`; branch placement makes the whole charter a proposal without document labels. Existing `main` content and logs remain intact, and canonical links continue to target `main`. For promotion, prepare a focused PR targeting `main` for external team review and approval, without collecting reviews, imposing a participation or absentee window, requiring PI/co-PI sign-off, or using a skill-managed human-review gate. Missing planning fields are called out in the PR/handoff for external resolution, not filled with invented facts or approval. Missing canonical identity or an unsafe/unconfirmed directory still blocks writes. Both paths require verified access and content screening.

Inspect the exact proposed content, including metadata, URLs, filenames, PR body, and the staged diff. Budgets and HR are linked rather than copied. Keep actual time-spent figures, raw transcripts, credentials, and restricted source material out of both branches and Git history. If a candidate contains prohibited content, stop before committing it and propose an explicitly authorized sanitized candidate that links restricted sources instead. Show any source/content change in the diff and hand it off for external PR review; do not silently change text, invent or transfer approval, or first commit then delete it. A rough deliverable size is planning information, not a finance actual.

**Done when:** the exact source revision, candidate bytes, target branch, safety check, permitted diff, and unresolved fields are established. External review is a PR handoff, not a prerequisite imposed by the skill for safe, authorized PR preparation. A changed source requires reselection and a refreshed diff; never claim it was reviewed based on an earlier revision.

## 5. Propose, merge, and verify publication

For proposal storage, create a focused candidate branch from the latest remote `develop`, named under the [ProjectStream submission rule](#projectstream-submission-rule), and a PR targeting `develop` in the authorized workspace. For the post-kickoff approval trigger, select the last user-approved `charter.md` under the [kickoff output contract](../SKILL.md#3-draft-the-charter), plus necessary project navigation/mapping changes, and preserve the charter's bytes; any necessary content changes require fresh user approval under the linked kickoff-submission step. For initial publication or an update to `main`, start a fresh branch from current `main` and copy only the exact selected candidate's charter bytes from the identified source revision. Do not use a whole `develop` merge: unrelated proposal content must remain absent from `main`. Confirm the canonical code, source commit, exact content diff, and unresolved fields in the PR; hand off team review and approval to the external GitHub PR process.

For an initial charter promotion, place an empty [decision log](decision-log-template.md) next to it, filling only established identity and immutable source commit/PR references. Remove the unused commented entry schema from the published empty log; it is a template, not a recorded decision. Keep the adjacent charter link relative. Do not fabricate approval, a first decision, or a transcript reference merely to initialize the log. Existing logs are preserved byte-for-byte, including their historical baseline reference; later decisions cite newer charter revisions in appended entries. Corrections append an entry identifying what it supersedes. Compare the proposed log against `main` and reject deletions, edits, reorderings, or duplicate entry IDs. Resolve a concurrent update against the latest `main`, recheck the selected charter and log, and refresh the PR diff/handoff if the candidate changes; earlier review is not evidence for changed bytes.

A charter-publication PR names the source revision, target branch, content diff, and unresolved fields; it does not solicit or certify PI/co-PI sign-off or collect team reviews. Opening the PR hands review and approval to the team outside the skill. Every AI-drafted decision entry goes through a PR with [the decision template](decision-pr-template.md); its existing AI/review fields remain for decisions, not as charter approval requirements. Any employee may review/merge decision PRs, self-merge included, subject to repository rules. Initializing an empty log is not transcript processing and generates no decisions. Automated extraction, conflict detection, and digests remain later Stories. Record reviewers and checked boxes only from verified evidence, never from PR creation or a requested merge.

Show the exact intended files, base branch, source revision, and diff before writes. Push/open a PR only under the requested publication authorization; opening a PR does not authorize a merge. Merge only on an explicit merge request, obeying observed repository rules and verifying any checks those rules require without bypassing them. Team review and approval remain outside the skill; do not impose an additional human-review gate or claim review you have not verified. Use existing credentials without reading or printing secrets. If a PR cannot merge or no merge is authorized, report it as proposed/pending rather than published. Keep the baseline snapshot retrievable by commit link, and synchronize only this project's merged state back to `develop` through a separately authorized focused PR, preserving unrelated proposals.

For an open submission PR, read back the remote topic-branch files and the PR's repository, base/head branches, exact file set, and open state; return its actual URL without claiming a merge. Read back merged files from the destination branch only after an authorized merge. Compare charter bytes to the selected source revision/candidate, check the adjacent log and append-only invariants, confirm the merged PR and commit, and verify no unrelated draft content reached `main`. On retry, inspect existing branches, PRs, and files first; an identical already-published snapshot needs no duplicate PR or log reset. Partial or failed operations remain explicit; never substitute an intended write for read-back evidence.

**Done when:** the exact content is verified on its destination branch or the PR/failure is clearly pending. Proposal storage on `develop` or an open promotion PR is not a published `main` snapshot. GitHub PRs carry the external review/approval history; a merged decision PR does not promote or certify a charter.

## 6. Link every project/activity repository and hand off

For a charter snapshot verified on `main`, produce the canonical `https://github.com/CUAHSI/CUAHSI-ProjectStream/blob/main/projects/<accounting-code>-<shortname>/charter.md` URL using the policy's exact directory mapping (reversible code component if needed) and URL-escaping the actual segment, and list every related repository recorded in the charter. For a rename, update active central and related-repository navigation to the new path without changing charter/log bytes or historical commit URLs. With explicit authorization, add a neutral charter link to each repository's README or existing project-navigation document through its normal PR process. Do not copy the charter or restricted source content. For public/nonstaff repositories, confirm that even the path/URL discloses no restricted identity before proposing it. If identity disclosure is restricted, obtain an approved neutral redirect/export handoff instead of posting the revealing URL. Missing permissions or authorization produce ready-to-review link proposals, not claimed edits.

Read back every merged link on its actual target branch and record URL/commit evidence in the central policy's navigation table. A multi-repository project is complete only when all relevant repositories have verified links, or the gaps are individually named. Do not edit the charter just to record operational link checks. Re-run access checks after configuration changes and keep private evidence in the authorized central policy/audit location.

Return branch/commit/PR URLs, canonical identity and source/merged revisions, confirmed shortname and exact directory/encoding mapping (old/new paths for a rename), PR/publication state and external review handoff, decision-log location, owner/delegations, access results, and per-repository link results. Display remaining blockers and next actors. Keep live project content and access rosters out of the ai-scaffolding checkout and Jira completion comments. The independent `project-report` workflow stays Jira-only and read-only; this workflow introduces no reporting, hosted MkDocs site, exports, transcript fetching, or email sending.

**Done when:** actual publication, access, and link outcomes are distinguishable from proposals and assumptions. Live acceptance needs a charter snapshot published to `main` through the external GitHub PR process, adjacent log, verified staff/nonstaff and employee merge checks, and verified links for every related repository; a tested reusable skill alone does not fulfill those operational checks.
