# Project report

Produce a leadership-facing account of delivered outcomes, significance, and outstanding work, grounded only in Jira evidence available at the reporting cutoff. Jira access is **read-only**. The report is both a local Markdown file and text in chat. Read [assets/evidence.md](assets/evidence.md) before classifying work; apply its rules to every item, including items with no period activity.

## 1. Establish the request

Require exactly one selector: an explicit Jira Research Project, Objective, or Epic root **or** a project label selecting current Research Projects, plus two unambiguous inclusive calendar dates (start and end). Accept unambiguous natural-language dates; echo the resolved ISO dates. Accept an optional timezone, a person or list of people, a destination directory, and a format: `summary` (default), `by-contributor`, or `brief`. Ask about missing or ambiguous selectors/dates; do not infer a selector or period. For a label, require an exact confirmed spelling: ask when no accessible Research Project matches or spelling is ambiguous; multiple exact matches are all in scope, not an ambiguity to resolve by picking one. Reject reversed ranges. If the end date is later than today **in the reporting timezone**, ask for a historical end date.

Use the authenticated Jira user's timezone from Jira's `/rest/api/3/myself` unless explicitly overridden; ask if no reliable timezone is available. Resolve natural-language dates to ISO dates before collection. Record the retrieval timestamp in UTC and the stated timezone. Calculate the window as `[local midnight at start, local midnight on the day after end)` using the named timezone (including daylight-saving changes), not a fixed UTC offset. For past end dates the cutoff is the exclusive end of that window; for an end date of today, use the retrieval time as cutoff and label the report **provisional through that time**. Apply the same cutoff to every evidence and state query. For an explicit root, confirm it is accessible and has the requested issue type; stop with an actionable explanation if not.

## 2. Collect the bounded Jira evidence

Check the invoking repository's Jira and credential guidance (for example `docs/agents/issue-tracker.md`), including its access boundaries. This reusable skill does not assume a CAM root or expand access to other projects. For label searches, use the Jira project key specified by repo guidance when the repo scopes Jira access; if scoped guidance does not establish that key, ask rather than search broadly. Distinguish Jira work-item write boundaries from read-only reporting boundaries; if a narrower read boundary applies, pass each permitted Research Project key as `--allowed-project-root <key>` (repeatable), or ask when permitted roots cannot be established. Otherwise search all accessible Jira projects for matching **Research Project** issues, including projects such as HydroFabric; do not silently substitute a familiar project or Objective. Use `acli` for ordinary access checks where suitable. With netrc-based REST credentials, use `assets/collect_evidence.py` (relative to this skill's directory) to collect the bounded source bundle: pass the explicit Jira `--site`, normalized selector and dates, and `--timezone` when overridden. Explicit-root invocation remains `<root> <start> <end>`; label invocation is `<label> <start> <end> --project-label [--project <Jira project key>] [--allowed-project-root <key> ...]`; pass `--project` and permitted root keys when required by the read scope. The helper uses GET-only `curl --netrc-file` and verifies private netrc permissions. Treat its JSON as sensitive working material: keep any temporary copy private, outside the repository, and remove it after reporting. If this helper is unavailable with the invoking repository's authentication, perform equivalent complete GET-only retrieval using that repository's guidance. Never print or copy credentials or perform Jira writes, even if another workflow normally assigns or transitions a ticket.

For a label, discover **all accessible current** exact-label Research Project matches within the permitted scope, paginating the search; confirm issue type and current label membership for each. Do not select only the first match or treat an incomplete search as a complete list. Collect **all accessible pages** of direct children recursively (including Sub-tasks) beneath each selected root, by `parent` relationship. With manual retrieval, Jira Cloud's `/rest/api/3/search/jql` uses `nextPageToken`; continue until `isLast` is true. If `isLast` is false with no next token, treat retrieval as incomplete, not as an empty page. Paginate comments from `/rest/api/3/issue/KEY/comment` and history from `/rest/api/3/issue/KEY/changelog` with `startAt`/`maxResults` until `total`; embedded issue comments and expanded changelogs are not exhaustive. Retrieve each item's identity, issue type, parent, created, status, resolution, assignee, schedule, description, and updated time. Use roots as organizational context; reportable work is their descendants. Ordinary issue links are context only, never additional members. Never fetch linked repositories, PRs, or documents to verify claims.

The explicit-root bundle retains its existing `root`, `period`, `items`, `partial`, `failures`, and `coverage` contract. The label bundle records the selector as `project_label` (string), `matched_projects` (each with `key` and `summary`), `roots` (root issue records), and flattened `items` (each with `reporting_root` set to its root key), plus `period`, `partial`, `failures`, and `coverage`. Include label search and inaccessible-root gaps in `failures`/`partial`; `coverage` must disclose that current label membership cannot establish historical membership. Both modes retain the same inclusive dates, timezone, cutoff, retrieval time, and provisional rule.

Audit the bundle's `failures` (`key`, `endpoint`, `page`, `reason`, and `field` for missing requested fields), each item's `comments_complete` and `changelog_complete` flags, and `excluded_comments` (comment IDs/times without post-cutoff or unverifiable text). Retain accessible pages; identify failed tickets, comments, pages, and fields and their effect on claims. An inaccessible explicit root, no usable label roots/descendants after retrieval failure, or otherwise insufficient evidence for a meaningful account requires an actionable stop, not an empty report. For a label with multiple matches, continue if one root fails but others support a meaningful account; mark **partial** and name the inaccessible root and its unsearched descendants. Successfully searched selected roots with no descendants support a qualified empty report. Otherwise continue with supported findings, marking **partial** whenever retrieval failed, even if no findings qualify. Disclose current-descendant and, for labels, current-label membership limits (historically labeled, moved-out, deleted, or inaccessible work may be absent) even for empty reports; exclude items created after cutoff. A retrieval error is not evidence of inactivity.

## 3. Reconstruct and assess

Apply [assets/evidence.md](assets/evidence.md) to **each descendant**, before writing prose. Use one working ledger row per key, tagged with its reporting root: parent, created time, cutoff-valid source citations, outcome date versus statement date, period-end lifecycle (or unknown), outstanding/abandoned work, and coverage gaps. Reconstruct status, resolution, assignment, and dated commitments as of the cutoff using complete relevant history; mark affected historical values unknown where history or requested fields are missing, never substituting today's values. Incomplete comments do not establish an absence of outcomes or credit. Only `comments` contains cutoff-valid text; describe relevant `excluded_comments` as a limitation without using their missing bodies. Assess descriptions against their changelog for post-cutoff edits; exclude unreconstructable earlier wording. Evaluate both period activity and period-end outstanding work, including untouched outstanding items; exclude previously completed/abandoned items unless context or a distinct period outcome requires them. Separate lifecycle state from planning assessment, deduplicate parent/child outcomes and reopenings, and preserve contradictions and unknowns. An explicit delivered outcome may be reported from an unfinished item without calling that item completed. Before prose, group findings under each matched Research Project for label reports and group ledger rows representing the same delivered result so it appears once (including across roots when applicable) with all relevant project associations and citations.

For person filters, resolve stable Jira account identities; ask if the intended identities cannot be distinguished. Filter **which work is presented**, not just headings: keep documented contributions and distinctly labeled assignment-based attribution for selected people, plus necessary collaborator context. Without a filter include all contributors and unknown-contributor work. Never infer contribution from the assignee, comment author, reporter, mentions, or a status-transition author.

## 4. Write and deliver

Prepare one of the following; length is a soft target, never a reason to drop a material caveat or citation:

- `summary`: roughly one page, grouped by outcome, with significance, outstanding/abandoned work, and material planning results.
- `by-contributor`: typically one to three concise bullets per contributor, distinguishing documented contribution from assignment-based attribution; retain shared credit and unknown attribution.
- `brief`: usually at most five accomplishment bullets, followed by compact outstanding/abandoned work and qualifications.

Include the explicit root and link, or the label selector and every matched Research Project name/key/link, inclusive dates, timezone, cutoff/retrieval time, format, people filter (or all), coverage/partial/provisional notes, ticket links for described work, and nearby Jira citations for every accomplishment and individual attribution. Link directly to a supporting comment when possible; otherwise cite the ticket and dated history event. Differentiate achieved dates from when statements were recorded. Label recorded claims as Jira evidence, not independently verified outcomes. Describe lifecycle and planning separately; omit default completion percentages, productivity rankings, and summed parent/child counts. If an unfiltered report has no qualifying findings, say **no qualifying evidence was found in the accessible evidence**; for an empty people-filtered report, say **no matching evidence was found in the accessible evidence**. Retain partial scope, unknowns, contradictions, and current-membership limitations rather than claiming inactivity or completeness.

Prepare the **complete report** in a private local draft outside the repository. From the invoking project's directory run `python3 <skill-directory>/assets/save_report.py <selector> <start> <end> <format> --source <private-draft> [--destination <directory>] [--project-label]`; pass `--project-label` only for a label selector. The default destination is its `reports/`. Explicit-root output stays `<root>_<start>_<end>_<format>_<generated-UTC>.md`; label output is `label-<slug>_<start>_<end>_<format>_<UTC>.md` (filesystem-safe label slug). The helper creates files exclusively and retries collisions with a suffix. Put the people filter in report metadata, not the filename. Display the same full report text in chat and the created path for ordinary, partial, and empty reports, with citations and qualifications intact. Remove the private draft after delivery. If writing fails, display its complete text, name the failure, mark delivery incomplete, and request a writable destination; do not claim a file was saved. The local artifact may contain internal Jira information: leave it unstaged and uncommitted; do not change ignore rules or publish it to Jira or elsewhere.

For implementation checks, exercise [assets/summary-scenarios.md](assets/summary-scenarios.md) at the request-to-report seam and run `python3 -m unittest discover -s tests` in this skill's source repository. These checks complement a read-only live Jira smoke run; fixture claims never enter live reports.
